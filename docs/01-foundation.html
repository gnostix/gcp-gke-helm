Remote state, providers, and APIs — everything later steps stand on.

Why two stacks?

Terraform state must live somewhere shared and durable (a GCS bucket), but Terraform can't store the state of the bucket inside the bucket it's creating. So bootstrap/ creates the bucket with local state, once. The root stack then uses that bucket as its gcs backend.

File tour

FileWhat it teaches
bootstrap/main.tfState bucket hardening: uniform access, public-access prevention, versioning (undo a bad state write), lifecycle to cap old versions, force_destroy=false.
versions.tfPin Terraform and provider versions. ~> 7.0 = any 7.x, never 8.0 — breaking changes are opt-in.
backend.tf + backend.hclPartial backend config. Backend blocks can't use variables, so the bucket is passed at init time. Same code, different environments.
providers.tfdefault_labels stamps every resource — cheap cost tracking and cleanup filters.
variables.tfTyped inputs with a validation block — fail at plan time, not halfway through apply.
apis.tffor_each over a set: one resource per API, addressed as google_project_service.this["container.googleapis.com"]. disable_on_destroy=false avoids breaking other users of the project.

Run it

# auth (once)
gcloud auth login
gcloud auth application-default login
gcloud config set project <PROJECT_ID>

# 1) bootstrap the state bucket
cd bootstrap
cp terraform.tfvars.example terraform.tfvars   # edit project_id
terraform init
terraform fmt -check && terraform validate
terraform apply
cd ..

# 2) root stack on remote state
cp backend.hcl.example backend.hcl             # bucket = <state_bucket output>
cp terraform.tfvars.example terraform.tfvars   # edit project_id
terraform init -backend-config=backend.hcl
terraform plan
terraform apply

Verify

gsutil ls gs://<PROJECT_ID>-tfstate/gke-lab/      # default.tfstate is there
gcloud services list --enabled | grep -E 'container|secretmanager|compute'
terraform state list                             # 5 google_project_service entries

Check your understanding

What happens if two people run apply at the same time?

The GCS backend takes a lock (a .tflock object). The second run waits or fails with a lock error instead of corrupting state.

Why for_each and not count for the APIs?

With count, resources are indexed 0..n. Remove an item from the middle and every later index shifts, so Terraform plans to destroy/recreate them. for_each keys by name, so removing one only touches that one.

Where would a GCP outage of Secret Manager show up?

Not here — enabling an API is just a project setting. It matters in Step 4/5 when pods read secrets at startup.
