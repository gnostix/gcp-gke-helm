Reading a 3rd-party chart before installing

helm show chart  oci://ghcr.io/stefanprodan/charts/podinfo --version 6.14.1   # metadata
helm show values oci://ghcr.io/stefanprodan/charts/podinfo --version 6.14.1   # every knob + defaults
helm template t  oci://ghcr.io/stefanprodan/charts/podinfo --version 6.14.1 \
  --set ui.color=#2f6fde | less                                            # the exact YAML it would apply

Always do this for software you don't control. Look for privileged containers, hostPath mounts, ClusterRoles, and Services of type LoadBalancer (cost).

Exercise — a controlled upgrade

git switch -c podinfo-6.15.0
# root main.tf:  chart_version = "6.15.0"
git commit -am "podinfo 6.14.1 → 6.15.0" && git push -u origin podinfo-6.15.0

In the PR plan you'll see ~ update in-place on helm_release with version: "6.14.1" → "6.15.0". After merge, helm -n podinfo history podinfo shows revision 2. A rollback is a revert PR, not helm rollback: Terraform owns the release, and a manual rollback would show up as drift.

Check your understanding

What happens if you omit version?

Helm installs the latest chart at that moment. A later terraform apply doesn't upgrade it on its own, but a new environment, or the morning re-apply after a destroy, silently gets whatever is newest. The same code then produces different clusters.

values vs set: which wins?

set. Helm merges in order: chart defaults → each values entry in order → set. Use values for structure and set for a single computed knob. set_sensitive hides a value from plan output.

Why can the pod pull from ghcr.io?

The node has a public IP (enable_nat = false). With private nodes you'd need Cloud NAT, or you'd mirror the image into Artifact Registry. That's the theme of 5c and of most regulated environments.
