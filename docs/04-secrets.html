Setup

# 1. GitHub → repo → Settings → Secrets and variables → Actions → Secrets tab
#    New repository secret:  DEMO_SECRET = hello-from-secret-manager

# 2. local plan only (never put it in terraform.tfvars):
export TF_VAR_demo_secret='hello-from-secret-manager'
terraform init -backend-config=backend.hcl     # registers module.secrets
terraform plan                                  # 3 to add, 1 to change

# 3. PR flow
git add -A && git commit -m "Step 4: Secret Manager + Workload Identity access"
git push -u origin step-4-secrets

Verify

gcloud secrets describe gke-lab-demo-secret --format="yaml(replication)"
gcloud secrets versions list gke-lab-demo-secret
gcloud secrets get-iam-policy gke-lab-demo-secret          # principal://…/ns/demo/sa/demo-app
gcloud secrets versions access latest --secret gke-lab-demo-secret   # you (Owner) can read it
kubectl get csidrivers                                      # secrets-store-gke.csi.k8s.io
terraform state pull | grep -c hello-from-secret-manager    # 0 → the value is NOT in state

Check your understanding

Why not just use secret_data?

It works, but the plaintext ends up in the state file (GCS bucket) and in saved plan files. Anyone with bucket read access, or with access to CI artifacts on a public repo, could read it.

Why grant to the Kubernetes SA instead of a Google service account?

Fewer moving parts: no GSA, no iam.gke.io/gcp-service-account annotation, no workloadIdentityUser binding. The older "GSA impersonation" pattern still works and is needed for a few APIs that don't support direct principals.

Who can read the secret right now?

Project Owners/Editors (you), the CI SA (secretmanager.admin), and pods running as demo/demo-app. Not the nodes, and not other pods. Even a pod in namespace demo with a different SA is denied.

For the Pfizer project?

Secrets created by app teams or a vault process (not Terraform), CMEK encryption, rotation schedules with Pub/Sub notifications, and one accessor binding per workload SA.
