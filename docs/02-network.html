File tour — modules/network/

FileWhat it teaches
versions.tfChild modules say which provider they need and a minimum version. They don't configure it: the root owns the provider block and the exact version in .terraform.lock.hcl.
variables.tfThe IP plan. Defaults live in the module, and the root can override them per environment.
main.tf5 resources. References like google_compute_network.this.id create implicit dependencies, so Terraform builds VPC → subnet → router → NAT in order without being told.
outputs.tfThe module's public API. GKE will consume the subnet and the names of its secondary ranges.
root main.tfmodule "network" { source = "./modules/network" } plus depends_on on the APIs: an explicit dependency, because no attribute links them.

Key design choices

VPC-native (alias IP) cluster. Pods get real VPC IPs from the secondary range, so they're routable inside the VPC and to peered networks/on-prem. That matters for the Pfizer case, where pods may talk to Slurm-side storage (Filestore, NFS) directly.
Private nodes + Cloud NAT. Nodes get no public IP. NAT gives them outbound-only internet. Google APIs go through Private Google Access instead, which is cheaper and doesn't count against NAT ports.
Minimal firewall. Implied rules already deny all ingress and allow all egress. GKE creates its own gke-… rules for control-plane→node and pod-to-pod traffic. We add only IAP SSH, scoped by network tag.
Cost & the enable_nat switch. VPC, subnet, router and firewall are free. Network resources are regional only, so there's no cheaper zonal variant. Cloud NAT costs $0.0014/VM-hour + $0.005/IP-hour + $0.045/GiB processed. The lab defaults to enable_nat = false: Router and NAT aren't created, and in Step 3 the node gets an ephemeral public IP instead (outbound works, inbound is still denied by the implied firewall rule). Set it to true to practise the production pattern of private nodes + NAT shown in the diagram.
Optional resources with count. count = var.enable_nat ? 1 : 0 makes a resource a list of 0 or 1. You then refer to it as google_compute_router.this[0]. That's why the NAT's router argument uses [0].

Check your understanding

Why does the pods range need to be so much bigger than the nodes range?

By default each node reserves a /24 (256 IPs) for up to 110 pods, even with only 3 pods running. A /16 pods range therefore caps the cluster at ~256 nodes. Running out of pod range is a classic GKE scaling wall, and you fix it with "additional pod ranges" or a smaller max_pods_per_node.

What breaks if you remove Cloud NAT?

Pulling images from public registries (Docker Hub, ghcr.io, quay.io) fails with ImagePullBackOff. Images from Artifact Registry still work, thanks to Private Google Access.

Why are source_ip_ranges_to_nat = ["ALL_IP_RANGES"] important?

With only PRIMARY_IP_RANGE, node VMs could reach the internet but pods (which use the secondary range) could not.

What would you change for production?

A Shared VPC host project owned by the network team, flow logs on, NAT with static (reserved) IPs if partners allowlist you, and the IP plan coordinated with on-prem to avoid overlap.
