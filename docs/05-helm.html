Before committing (on your Mac)

git switch -c step-5-helm                      # new files come along

# 1. confirm the DNS endpoint has a publicly trusted cert (we don't pass a CA):
EP=$(terraform output -json gke | jq -r .dns_endpoint)
curl -sS -o /dev/null -w "%{http_code}\n" https://$EP/version
#   any HTTP code (401/403/200) = TLS OK.  "SSL certificate problem" = tell me, we add the CA.

# 2. register the helm provider + module, refresh the lock for both platforms
terraform init -backend-config=backend.hcl
terraform providers lock -platform=darwin_arm64 -platform=linux_amd64

# 3. optional: lint + render the chart locally
helm lint charts/demo-app --set secret.resourceName=x
helm template demo charts/demo-app --set secret.resourceName=projects/p/secrets/s/versions/latest

# 4. local plan (needs the secret var because it's a required input)
export TF_VAR_demo_secret='…'
terraform plan            # expect: 1 to add (module.app.helm_release.this)

Verify after merge

git switch main && git pull
kubectl -n demo get all,secretproviderclass,sa
helm -n demo list                               # release demo-app, STATUS deployed
$(terraform output -raw port_forward)           # http://localhost:8080
kubectl -n demo get secrets                     # only Helm's release record. The value is NOT a K8s Secret

Prove the security model

# same image, same namespace, DIFFERENT service account (default) → mount is denied
kubectl -n demo run intruder --image=busybox:1.37 --restart=Never \
  --overrides='{"spec":{"volumes":[{"name":"s","csi":{"driver":"secrets-store-gke.csi.k8s.io","readOnly":true,"volumeAttributes":{"secretProviderClass":"demo-app-secrets"}}}],"containers":[{"name":"c","image":"busybox:1.37","command":["sleep","3600"],"volumeMounts":[{"name":"s","mountPath":"/s"}]}]}}'
kubectl -n demo describe pod intruder | tail -5  # FailedMount … PermissionDenied
kubectl -n demo delete pod intruder

Check your understanding

Who installs the release, and with what Kubernetes permissions?

In CI: the github-terraform SA, whose IAM role container.admin GKE maps to full Kubernetes API access. Locally: you (Owner). Kubernetes RBAC applies in addition to IAM. Either one can grant access.

Why does a failed secret mount fail the Terraform apply?

wait = true: Helm waits for the Deployment to be Ready. A pod stuck in ContainerCreating (FailedMount) never becomes Ready, so after 300 s the release is marked failed and the apply errors, with the reason in kubectl describe pod.

Why exec instead of token = data.google_client_config.x.access_token?

Data-source results are stored in the saved plan, and our plan is uploaded as an artifact (publicly downloadable on a public repo). An exec plugin fetches the token at the moment of use, so it's never written down.

Caveat: cluster and Helm in one stack

The Helm provider is configured from module.gke outputs. Creating everything from zero in one apply (the morning apply after a destroy) usually works, because creating a release doesn't need the cluster at plan time. If it ever fails at plan, the fix is a two-phase apply (cluster first, then app), or moving apps to their own stack or GitOps, which is what we'll discuss in the extensions.
