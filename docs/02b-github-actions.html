How the login works (Workload Identity Federation)

No JSON key exists anywhere. The thing GitHub stores (GCP_WIF_PROVIDER, GCP_CI_SA) is just an address. It's useless unless the request carries a token signed by GitHub for your repo.

Setup — once

  1. Create the GitHub repo and push (you've done this).
  2. Add the repo to bootstrap and apply locally: 
    cd bootstrap
echo 'github_repo = "<owner>/gcp-gke-helm"' >> terraform.tfvars
terraform plan      # 17 to add: 4 APIs, pool, provider, SA, 10 IAM bindings
terraform apply
terraform output github_variables
  3. GitHub → repo → Settings → Secrets and variables → Actions → Variables tab → add the 4 values from the output.
  4. GitHub → Settings → Environments → New environment gcp-lab. Add yourself under Required reviewers for a manual approval gate. On a private repo this needs a paid GitHub plan; without it, the environment still works, just with no gate.
  5. Make the provider lock file valid for Linux runners, then commit: 
    cd ..
terraform providers lock -platform=darwin_arm64 -platform=linux_amd64
git checkout -b step-2-network
git add -A && git commit -m "CI: GitHub Actions + network module"
git push -u origin step-2-network     # open a PR → watch the plan comment
  6. Merge the PR → the workflow applies the network (3 resources).

Verify

gcloud iam workload-identity-pools providers describe github-oidc \
  --location=global --workload-identity-pool=github --format="value(attributeCondition)"
gcloud projects get-iam-policy $PROJECT --flatten=bindings[].members \
  --filter="bindings.members:github-terraform" --format="value(bindings.role)"

Check your understanding

Why does WIF live in bootstrap and not the root stack?

Chicken-and-egg: CI can't create the identity it needs to log in. Anything CI depends on to run at all (state bucket, its own identity) is created once by a human.

Why is attribute_condition essential?

Every repo on GitHub can get a token from token.actions.githubusercontent.com. Without the condition, any GitHub user could exchange their token at your pool. The IAM binding filters again, but the condition rejects them at the door.

Why apply a saved plan instead of running terraform apply again?

Between plan and apply, someone may change things. Applying the saved file guarantees you get what was reviewed, and Terraform refuses if the state moved ("Saved plan is stale").

What would harden this for the Pfizer project?

Separate read-only plan SA (PRs) and apply SA (only attribute.ref == refs/heads/main), match on repository_id instead of name (repo-rename squatting), IAM Conditions on projectIamAdmin, and pinning actions to commit SHAs.
